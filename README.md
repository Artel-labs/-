Новая версия сайта Центра дополнительного профессионального образования. Переписана с нуля
на готовых фреймворках вместо самописного кода прежней версии
([itspecR/dpo-pravo-hse](https://github.com/itspecR/dpo-pravo-hse)). Дизайн сохранён.

> [!TIP]
> **Установка в двух словах.** Чистый сервер Ubuntu 24.04 → скачать код в `~/dpo` →
> `sudo ./scripts/install.sh` → сохранить пароль администратора, который скрипт покажет один раз →
> открыть адрес, который скрипт напишет в конце. Вопросов скрипт не задаёт, Docker ставит сам.
> Подробно — в разделе [Установка с нуля на Ubuntu](#установка-с-нуля-на-ubuntu).

## Что делает

| Кто | Что видит и делает |
|---|---|
| 👤 Посетитель сайта | Главная, каталог с фильтрами, поиском и сравнением, страницы программ, рейтинги, политика ПДн, форма заявки, бот поддержки (ворона) |
| 📱 Пользователь Telegram | Мини-приложение `/tg/`: сферы права, поиск, карточка программы, заявка (пока демонстрационная; открыто только на тестовом стенде) |
| 🗂 Сотрудник Центра | Админка `/admin/`: каталог программ, заявки и получатели писем, посещаемость, фоновые задачи |
| 🛠 Администратор сервера | Скрипты в `scripts/`: установка, обновление, резервные копии, HTTPS, сброс пароля и двухфакторного входа |

Что происходит само, без участия людей:

| Когда (Москва) | Что |
|---|---|
| каждый день 03:00 | резервная копия базы и загруженных файлов, очистка истёкших сессий админки; раз в `LOG_RETENTION_DAYS − 1` дней — пересоздание контейнеров сайта, чтобы их журналы (IP, браузер, адрес страницы) хранились не дольше `LOG_RETENTION_DAYS` дней (сайт недоступен 10–30 секунд) |
| каждый день 03:30 | удаление заявок: рассмотренных — через `APPLICATION_CLOSED_RETENTION_DAYS` дней после итога, любых — через `APPLICATION_MAX_RETENTION_DAYS` дней после получения |
| каждый день 03:40 | удаление событий посещаемости старше `ANALYTICS_RETENTION_DAYS` дней |
| каждый день 03:50 | удаление записей журнала входов в админку старше `AXES_LOG_RETENTION_DAYS` дней |
| два раза в сутки, 00:00 и 12:00 | обновление каталога со страницы программ факультета на hse.ru |
| после каждой заявки | письмо получателям; если не ушло — повтор через 5 минут, всего до 3 попыток |

## Стек

| Слой | Технология | Зачем |
|---|---|---|
| Публичный сайт | Astro 7 (SSR на Node.js 24), TypeScript | страницы собираются на сервере из данных Django, без JS по умолчанию |
| Сервер | Django 5.2 LTS, django-ninja, gunicorn | API для сайта, бизнес-правила, админка |
| Админка | Django Admin с темой Unfold | каталог, заявки, аналитика |
| Вход в админку | django-axes, TOTP-коды | защита от подбора пароля, двухфакторный вход |
| Фоновые задачи | django-q2 (контейнер `worker`) | письма по заявкам, обновление каталога, ночная очистка |
| База данных | MariaDB 11.8.9 (в контейнере) | все данные сайта |
| Веб-сервер | nginx 1.30 | HTTPS, раздача файлов, кэш страниц на 60 секунд, ограничение частоты запросов |
| Развёртывание | Docker Compose, скрипты bash в `scripts/` | установка одной командой, обновление с откатом |
| Проверки | pytest, ruff, mypy (strict), ESLint, astro check, shellcheck, GitHub Actions | каждое изменение проверяется, включая полную установку на чистой машине |

## Как всё работает

```
                         сервер Ubuntu
              ┌───────────────────────────────────────────────────────────┐
              │  Docker Compose, проект «dpo»                             │
  браузер     │                                                           │
  ─────────►  │  web (nginx) ──── страницы ───► site (Node.js + Astro) ─┐ │
  HTTP_PORT   │     │                                                   │ │
  HTTPS_PORT  │     └── /api/, /admin/, /static/ ──► app (gunicorn ◄────┘ │
              │                                         + Django)         │
              │                                           │               │
              │                     worker (django-q2) ───┤               │
              │                                           ▼               │
              │                                     db (MariaDB)          │
              │                                                           │
              │  тома Docker: dpo_db-data (база), dpo_media (обложки,     │
              │  фото, документы)                                         │
              │  на диске сервера: .env, /etc/dpo/tls, /var/backups/dpo   │
              └───────────────────────────────────────────────────────────┘
```

| Компонент | Контейнер | Слушает внутри | Виден из сети | Предел памяти |
|---|---|---|---|---|
| nginx | `web` | 80, 443 | ✅ да, на портах `HTTP_PORT` и `HTTPS_PORT` сервера | 256 МБ |
| Astro (страницы) | `site` | 4321 | ❌ нет, только для `web` | 512 МБ |
| Django + gunicorn | `app` | 8000 | ❌ нет, только для `web` и `site` | 1 ГБ |
| Фоновые задачи | `worker` | — | ❌ нет | 512 МБ |
| MariaDB | `db` | 3306 | ❌ нет, только внутри Docker | 1 ГБ |

Наружу открыт только `web`. Логи каждого контейнера — не больше 5 файлов по 10 МБ.

## Требования к серверу и порты

**Система.** Ubuntu Server 24.04 LTS. Именно на ней установка проверяется в GitHub Actions при
каждом изменении. На других версиях Ubuntu и других дистрибутивах установка не проверялась.

**Доступ.** Пользователь с правами `sudo` и вход по SSH. Работать под `root` не нужно.

**Интернет на сервере.** Нужен при установке и обновлении:

| Куда | Зачем |
|---|---|
| Docker Hub (`registry-1.docker.io`) | образы `mariadb`, `python`, `node`, `nginx` |
| PyPI (`pypi.org`, `files.pythonhosted.org`) | библиотеки Python при сборке `app` |
| npm (`registry.npmjs.org`) | библиотеки сайта при сборке `site` и `web` |
| зеркало пакетов Ubuntu | пакеты `git`, `curl`, `openssl`, `iproute2`, `docker.io`, `docker-compose-v2` |
| GitHub | код сайта (если ставите через git) |

Во время работы сервер ходит только на `www.hse.ru` (обновление каталога) и на почтовый сервер
из `SMTP_HOST`. Скрипт мини-приложения `telegram.org/js/telegram-web-app.js` загружает браузер
посетителя, а не сервер, и только на тестовом стенде.

**Адрес.** Постоянный IP-адрес или домен. Без домена сайт работает по IP с самоподписанным
сертификатом.

**Железо.**

| | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 2 vCPU | 4 vCPU |
| Память | 4 ГБ | 8 ГБ |
| Диск | 25 ГБ SSD | 50 ГБ SSD |

<details>
<summary>Откуда эти цифры</summary>

Замер на тестовой установке 04.10.2026 (34 программы с обложками и фото):

- память в простое: все пять контейнеров вместе — около 0,5 ГБ (`docker stats`); пределы памяти
  в `docker-compose.yml` в сумме — 3,25 ГБ;
- образы Docker — 3,3 ГБ (`docker system df`), кэш сборки после многих пересборок — 5,1 ГБ;
- база — 172 МБ, загруженные файлы — 25 МБ;
- одна резервная копия — около 23 МБ (база 0,1 МБ + файлы 23 МБ), 30 копий — около 0,7 ГБ.

Пиковое потребление памяти во время сборки не замерялось, а на сервере с 2 ГБ памяти установка
не проверялась — поэтому минимум взят с запасом. Минимум и рекомендация — оценка по этому замеру,
а не требования производителей.

</details>

**Порты.**

| Порт | Кто слушает | Нужно открыть наружу |
|---|---|---|
| 22/tcp | SSH | ✅ да (для администратора) |
| `HTTP_PORT` (80, если свободен) | nginx, перенаправляет на HTTPS | ✅ да |
| `HTTPS_PORT` (443, если свободен) | nginx, сайт и админка | ✅ да |

Скрипт установки сам выбирает первую свободную пару: 80/443 → 8080/8443 → 8081/8444 →
8082/8445 → 8083/8446. Например, если на сервере уже работает другой сайт на 80 и 443, наш
займёт 8080 и 8443. Задать порты вручную: `sudo env HTTP_PORT=8080 HTTPS_PORT=8443 ./scripts/install.sh`.

Брандмауэр `ufw` (если используете):

> [!WARNING]
> Сначала разрешите SSH и только потом включайте `ufw`, иначе потеряете доступ к серверу.

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

Если скрипт выбрал другие порты, откройте их вместо 80 и 443 (они записаны в `~/dpo/.env`).

> [!NOTE]
> Docker сам открывает опубликованные порты контейнеров в обход правил `ufw`. Поэтому порты сайта
> будут доступны снаружи и без правил выше, а закрыть их одним `ufw` не получится. Остальные
> контейнеры (база, Django, Astro) портов на сервере не публикуют вовсе.

## Установка с нуля на Ubuntu

Ниже — весь путь от только что созданного сервера до работающего сайта. Код ставится в папку
`~/dpo` (домашняя папка пользователя, под которым вы зашли). Можно выбрать любую другую — скрипты
находят свою папку сами.

### Шаг 0. Подготовьте сервер

1. Зайдите на сервер по SSH под пользователем с `sudo`:

   ```bash
   ssh <пользователь>@<IP сервера>
   ```

2. Обновите систему и поставьте git (на Ubuntu Server он обычно уже есть):

   ```bash
   sudo apt update && sudo apt upgrade -y
   sudo apt install -y git
   ```

   Если после обновления есть файл `/var/run/reboot-required`, перезагрузитесь: `sudo reboot`,
   затем снова зайдите по SSH.

3. Если нужен брандмауэр — настройте его по разделу [Требования к серверу и порты](#требования-к-серверу-и-порты).

Docker заранее ставить не нужно: скрипт установки поставит его сам из репозитория Ubuntu
(`docker.io` и `docker-compose-v2`). Если Docker с Compose v2 уже установлен, скрипт его не трогает.

### Шаг 1. Скачайте код

Репозиторий приватный. Выберите один из трёх вариантов.

> [!IMPORTANT]
> Пока новая версия не влита в `main`, указывайте нужную ветку: при клонировании —
> `git clone -b <ветка> …`, при обновлении — `./scripts/deploy.sh <ветка>`, при скачивании
> архива — переключитесь на ветку в GitHub перед «Download ZIP».

<details open>
<summary><b>Вариант А. Ключ доступа только на чтение (deploy key) — рекомендуется</b></summary>

Ключ даёт серверу доступ только к этому репозиторию и только на чтение. Обновления потом
скачиваются без паролей.

1. Создайте ключ на сервере и покажите его открытую часть:

   ```bash
   ssh-keygen -t ed25519 -N "" -f ~/.ssh/dpo_deploy
   cat ~/.ssh/dpo_deploy.pub
   ```

2. В GitHub откройте репозиторий → **Settings** → **Deploy keys** → **Add deploy key**. Название —
   любое (например, имя сервера), в поле **Key** вставьте строку, которую показала команда `cat`.
   Галочку **Allow write access** не ставьте. Нажмите **Add key**.

3. Склонируйте репозиторий и закрепите ключ за ним:

   ```bash
   GIT_SSH_COMMAND="ssh -i ~/.ssh/dpo_deploy" git clone git@github.com:itspecR/dpo-pravo-hse-v2.git ~/dpo
   cd ~/dpo
   git config core.sshCommand "ssh -i ~/.ssh/dpo_deploy"
   ```

   При первом подключении ssh спросит, доверять ли github.com, — ответьте `yes`.

</details>

<details>
<summary><b>Вариант Б. Личный токен GitHub</b></summary>

1. В GitHub: аватар → **Settings** → **Developer settings** → **Personal access tokens** →
   **Fine-grained tokens** → **Generate new token**.
2. **Repository access** → **Only select repositories** → `itspecR/dpo-pravo-hse-v2`.
   **Permissions** → **Contents**: **Read-only**. Срок действия — на ваше усмотрение.
3. Склонируйте репозиторий. Git спросит логин и пароль: логин — ваш логин GitHub, вместо пароля
   вставьте токен.

   ```bash
   git clone https://github.com/itspecR/dpo-pravo-hse-v2.git ~/dpo
   cd ~/dpo
   ```

4. Чтобы при обновлениях не вводить токен каждый раз:

   ```bash
   git config credential.helper store
   ```

   После следующего ввода токен сохранится в `~/.git-credentials` в открытом виде.

> [!CAUTION]
> Не вставляйте токен в адрес репозитория (`https://<токен>@github.com/…`): он останется в
> `.git/config` и в истории команд. Когда срок токена истечёт, обновления перестанут скачиваться —
> выпустите новый токен и введите его при следующем обновлении.

</details>

<details>
<summary><b>Вариант В. Архив без доступа сервера к GitHub</b></summary>

1. На своём компьютере откройте репозиторий в GitHub → **Code** → **Download ZIP**. Получится файл
   вида `dpo-pravo-hse-v2-main.zip` (в имени — ветка).
2. Скопируйте архив на сервер:

   ```bash
   scp dpo-pravo-hse-v2-main.zip <пользователь>@<IP сервера>:~
   ```

3. На сервере распакуйте его в `~/dpo`:

   ```bash
   sudo apt install -y unzip
   unzip dpo-pravo-hse-v2-main.zip
   mv dpo-pravo-hse-v2-main ~/dpo
   cd ~/dpo
   chmod +x scripts/*.sh
   ```

   Для архива `.tar.gz` вместо `unzip`: `tar -xzf dpo-pravo-hse-v2-main.tar.gz`.

Серверу всё равно нужен интернет для Docker Hub, PyPI и npm — из архива ставится только код.
Обновление из архива описано в разделе [Обновление](#обновление).

</details>

### Шаг 2. Запустите установку

```bash
cd ~/dpo
sudo ./scripts/install.sh
```

Одна команда, вопросов она не задаёт. На медленном канале скачивание и сборка занимают
5–10 минут. Не прерывайте установку: при сбое сети скрипт сам повторит попытку (до 5 раз
с паузой 10 секунд).

Варианты запуска:

| Команда | Что будет |
|---|---|
| `sudo ./scripts/install.sh` | HTTPS с самоподписанным сертификатом на IP сервера (по умолчанию) |
| `sudo ./scripts/install.sh --https example.ru www.example.ru` | то же, но сертификат и список разрешённых адресов включают указанные домены или IP; адрес сайта в `SITE_URL` — первый из них |
| `sudo ./scripts/install.sh --http` | только HTTP, без сертификата — **только для тестового стенда** (`SITE_MODE=test`); HTTPS можно включить позже |
| `sudo env HTTP_PORT=8080 HTTPS_PORT=8443 ./scripts/install.sh` | свои порты вместо автоматического выбора |

### Шаг 3. Сохраните пароль администратора

На шаге «[5/7] Создаём администратора» скрипт покажет:

```
Логин:  admin
Пароль: <случайный пароль>
Пароль показан один раз — сохраните его. Сменить: ./scripts/reset-admin-password.sh
```

> [!IMPORTANT]
> Пароль больше нигде не хранится в открытом виде и повторно не показывается. Если не успели
> сохранить — задайте новый: `./scripts/reset-admin-password.sh`.

В конце скрипт напишет адреса, например:

```
Готово. Сайт: https://203.0.113.10/  Админка: https://203.0.113.10/admin/
```

Если порты 80/443 были заняты, в адресе будет порт: `https://203.0.113.10:8443/`.

### Шаг 4. Перезайдите по SSH

Скрипт добавил вашего пользователя в группу `docker`. Чтобы это подействовало, выйдите и зайдите
снова:

```bash
exit
ssh <пользователь>@<IP сервера>
```

После этого `docker compose …`, `./scripts/update.sh` и скрипты администраторов запускаются
без `sudo`. Скрипты, которые меняют систему (`install.sh`, `setup-https.sh`, `backup.sh`,
`restore.sh`, `backup-timer.sh`), по-прежнему запускаются через `sudo`.

### Шаг 5. Проверьте, что всё работает

```bash
cd ~/dpo
docker compose ps                          # пять контейнеров, у db, app и site — (healthy)
curl -fsSk https://127.0.0.1/api/health    # ответ сайта; при другом порте: https://127.0.0.1:8443/api/health
sudo ./scripts/backup-timer.sh status      # таймер резервной копии и время следующего запуска
```

Откройте в браузере адрес сайта. Браузер один раз предупредит о самоподписанном сертификате —
это ожидаемо, подтвердите переход. Затем откройте `/admin/` и войдите как `admin`.

### Шаг 6. Первичная настройка в админке

1. **Двухфакторный вход.** Меню пользователя справа вверху → «Двухфакторный вход» → отсканируйте
   код приложением-аутентификатором (Яндекс Ключ, Google Authenticator и др.).
2. **Сотрудники.** «Пользователи» → «Добавить» — отдельная учётная запись для каждого. Пароль — не
   короче 12 символов.
3. **Кому приходят заявки.** «Заявки» → «Получатели писем»: адрес (только @hse.ru), темы, отметка «Получает письма».
4. **Почта.** Заполните `SMTP_*` в `~/dpo/.env` — по разделу [Как подключить почту](#как-подключить-почту).
5. **Каталог** уже заполнен данными прежнего сайта и каждую ночь обновляется с hse.ru — см.
   [Каталог программ](#каталог-программ).

## HTTPS

По умолчанию `install.sh` сразу включает HTTPS. Включить его позже (после установки с `--http`)
или добавить домен:

```bash
sudo ./scripts/setup-https.sh [домен-или-IP ...]
```

Скрипт:

1. создаёт самоподписанный сертификат на 825 дней в `/etc/dpo/tls` (`fullchain.pem`, `privkey.pem`);
   в сертификат попадают `localhost`, `127.0.0.1`, все IP сервера и указанные домены или IP;
2. включает защищённые cookie (`COOKIE_SECURE=1`), дописывает указанные адреса в
   `DJANGO_ALLOWED_HOSTS`, записывает в `SITE_URL` первый указанный адрес (или IP сервера),
   переключает сайт в боевой режим (`SITE_MODE=production`);
3. перезапускает `app`, `worker` и `web`.

Если в `.env` стоит `SMTP_ALLOW_INSECURE_AUTH=1`, скрипт ничего не меняет и просит сначала убрать
эту строку: в боевом режиме почта только с шифрованием.

### Боевой и тестовый режим

`SITE_MODE` в `.env`: `production` — боевой сервер, `test` — тестовый стенд. Если строки нет,
сайт считает себя боевым. В боевом режиме сайт не запустится, если:

- не включён HTTPS (`COOKIE_SECURE` не `1` или `SITE_URL` не начинается с `https://`);
- в `.env` стоит `SMTP_ALLOW_INSECURE_AUTH=1`.

Причина пишется в журнал: `docker compose logs --tail=20 app`. `install.sh --http` записывает
`SITE_MODE=test`, `setup-https.sh` — `SITE_MODE=production`. При обновлении сервера без этой строки
`update.sh` допишет `production`, если HTTPS включён, иначе `test` и предупреждение.

После этого HTTP-порт перенаправляет на HTTPS (с нужным портом, если он не 443).

> [!NOTE]
> Сертификат самоподписанный: браузер предупредит о нём один раз на каждом устройстве.
> Сертификат Let's Encrypt для настоящего домена будет добавлен отдельным шагом, когда домен
> будет известен. Через 825 дней сертификат нужно перевыпустить той же командой.

## Резервные копии

Копия — это два зашифрованных файла: база `dpo-<дата>.sql.gz.enc` и загруженные файлы сайта
(обложки, фото, документы) `dpo-<дата>.media.tar.gz.enc`. Хранятся в `BACKUP_DIR` (по умолчанию
`/var/backups/dpo`, доступ только root), не дольше `BACKUP_MAX_AGE_DAYS` дней (по умолчанию 30) и не
больше `BACKUP_KEEP` штук (по умолчанию 30). Копии старше срока удаляются при каждом новом копировании.

### Шифрование копий

Копия шифруется ещё до записи на диск (`openssl cms`, AES-256) открытым ключом сервера
`/etc/dpo/backup-key/backup.crt`. Расшифровать её можно только закрытым ключом, который на сервере
храниться не должен. Пару ключей создаёт `install.sh`, а на старых серверах — первая копия после
обновления. Закрытый ключ сначала лежит в `/etc/dpo/backup-key/private-key-move-off-server.pem`, и
пока он там, каждая копия напоминает о нём. Что сделать один раз:

1. Скопируйте ключ к себе (файл принадлежит root):
   `sudo cp /etc/dpo/backup-key/private-key-move-off-server.pem ~/dpo-backup-key.pem && sudo chown $USER ~/dpo-backup-key.pem`,
   затем со своего компьютера: `scp '<пользователь>@<IP сервера>:~/dpo-backup-key.pem' .`
2. Сохраните ключ в двух надёжных местах вне сервера (например, в хранилище паролей и на
   защищённом носителе). Без него копии не восстановить.
3. Удалите ключ с сервера: `sudo shred -u /etc/dpo/backup-key/private-key-move-off-server.pem ~/dpo-backup-key.pem`.

Для восстановления ключ временно кладут на сервер и указывают в `--key`, после восстановления его
снова удаляют (`shred -u`). Копии, сделанные до шифрования (`.sql.gz` без `.enc`), восстанавливаются
без ключа.

После восстановления из копии сразу удаляются данные с истёкшим сроком хранения — заявки,
аналитика и журнал входов, — чтобы старая копия не вернула то, что уже было удалено по сроку.
То же вручную: `sudo docker compose exec app python manage.py purge_expired`.

| Команда | Что делает |
|---|---|
| — | автоматически каждый день в 03:00 по Москве (таймер systemd `dpo-backup`); если сервер в это время был выключен, копия делается после включения |
| `sudo ./scripts/backup.sh` | копия прямо сейчас |
| `sudo ./scripts/restore.sh` | список последних 10 копий |
| `sudo ./scripts/restore.sh <файл .sql.gz.enc> --key <закрытый ключ>` | восстановление базы и файлов, затем удаление данных с истёкшим сроком; перед этим сохраняет текущее состояние, просит ввести `ВОССТАНОВИТЬ` |
| `sudo ./scripts/restore.sh <файл .sql.gz.enc> --key <закрытый ключ> --yes` | то же без вопроса |
| `sudo ./scripts/backup-timer.sh status` | когда следующая копия |
| `sudo ./scripts/backup-timer.sh install` / `remove` | включить или выключить таймер; после обновления до версии с `rotate-logs.sh` выполните `install` ещё раз |
| `sudo ./scripts/rotate-logs.sh --now` | пересоздать контейнеры сайта и удалить их журналы сейчас |

Секреты двухфакторного входа хранятся в базе зашифрованными, ключ `TWO_FACTOR_KEY` лежит в `.env`
и в копию не попадает. Восстановить копию с рабочим двухфакторным входом можно только с тем же
ключом: при переносе на новый сервер перенесите и `.env`. С другим ключом пользователи с включённым
двухфакторным входом не смогут войти, пока его не сбросить: `sudo ./scripts/disable-two-factor.sh <логин>`.

> [!WARNING]
> Копии лежат на том же сервере. Если сервер пропадёт, пропадут и они. Регулярно забирайте
> свежую пару файлов на другой компьютер или в хранилище. Файлы зашифрованы, их можно хранить
> где угодно отдельно от закрытого ключа. Файлы принадлежат root, поэтому сначала скопируйте их
> на сервере в свою папку и отдайте себе:
> `sudo cp /var/backups/dpo/dpo-<дата>.* ~ && sudo chown $USER ~/dpo-<дата>.*`,
> затем со своего компьютера: `scp '<пользователь>@<IP сервера>:~/dpo-<дата>.*' .`

<details>
<summary>Перенос сайта на другой сервер</summary>

1. На старом сервере: `sudo ./scripts/backup.sh`, заберите оба файла последней копии.
2. На новом сервере установите сайт с нуля (шаги 0–4).
3. Положите оба файла копии в одну папку на новом сервере и восстановите с закрытым ключом:
   `sudo ./scripts/restore.sh <путь>/dpo-<дата>.sql.gz.enc --key <путь>/dpo-backup-key.pem`,
   затем удалите ключ с сервера. Чтобы новые копии шифровались тем же ключом, перенесите и
   `/etc/dpo/backup-key/backup.crt`; иначе первая копия создаст новую пару ключей.
4. Пароли администраторов и двухфакторный вход переедут вместе с базой.

Этот сценарий собран из тех же скриптов, но целиком на двух разных серверах не проверялся.
Резервная копия и восстановление на одном сервере проверяются в GitHub Actions при каждом изменении.

</details>

## Администраторы и забытый пароль

| Ситуация | Что делать |
|---|---|
| Первый администратор | `admin` создаётся при установке, пароль показывается один раз |
| Нужен ещё сотрудник | админка → «Пользователи» → «Добавить»; пароль — не короче 12 символов |
| Забыли пароль | `./scripts/reset-admin-password.sh [логин]` — покажет новый случайный пароль и снимет блокировку входа. Без логина сработает, если администратор один; если их несколько, скрипт перечислит логины |
| Потерян телефон с кодами | `./scripts/disable-two-factor.sh [логин]` — отключит двухфакторный вход (без логина — если он включён только у одного) |
| Вход заблокирован после неверных попыток | подождать 15 минут или снять все блокировки: `docker compose exec app python manage.py axes_reset` |
| Администраторов нет совсем | `./scripts/create-admin.sh` |

Двухфакторный вход каждый сотрудник включает себе сам: меню пользователя → «Двухфакторный вход».
Вход идёт в два шага: логин и пароль, затем — только если защита включена — отдельная страница
с шестизначным кодом (действует 5 минут). Неверный код считается неудачной попыткой входа.

| Признак | Причина и что делать |
|---|---|

| `Не нашлось свободных портов из списка` | Заняты все пары от 80/443 до 8083/8446 — задайте свои, как в строке выше |

Проверьте: `curl -I https://registry-1.docker.io/v2/`, `curl -I https://registry.npmjs.org/`, `curl -I https://pypi.org/` |
| `permission denied … docker.sock` | Вы ещё не перезашли по SSH после установки (шаг 4) |
| `Нет файла .env … Сначала запустите: sudo ./scripts/install.sh` | Скрипт запущен не в той папке или установка ещё не делалась |
| `Сайт не ответил за 60 секунд` | Смотрите состояние и логи: `docker compose ps`, `docker compose logs --tail=50 app site web` |
| Браузер пишет, что сертификат ненадёжный | Так и должно быть с самоподписанным сертификатом — подтвердите переход один раз |
| `Bad Request (400)` при входе по домену | Домена нет в `DJANGO_ALLOWED_HOSTS`. Выполните `sudo ./scripts/setup-https.sh <домен>` или допишите домен в `.env` и выполните `docker compose up -d app` |
| `429 Too Many Requests` на странице входа | Слишком частые попытки — подождите минуту |
| Вход не проходит даже с верным паролем | После 5 неверных попыток вход заблокирован на 15 минут: подождите или выполните `./scripts/reset-admin-password.sh <логин>` |
| Письма по заявкам не приходят | Админка → «Заявки» → блок «Состояние почты» и кнопка «Проверить почту»; проверьте получателей писем; логи: `docker compose logs --tail=100 worker` |

| Обновление упало | Прошлая версия уже возвращена автоматически. Причина — в выводе скрипта; при ошибках в работе сайта восстановите копию командой из вывода |
| `no space left on device` | Освободите место: `docker builder prune` (кэш сборки) и `docker image prune` (неиспользуемые образы); данные сайта эти команды не трогают |
| Правка в админке не видна на сайте | Страницы кэшируются на 60 секунд — подождите минуту |

Полезные команды:


## Каталог программ

Каталог правится в админке: «Каталог программ» → «Программы», «Направления», «Преподаватели».
У программы есть вкладки: основное, условия, описание, объявление, а также программа обучения,
преподаватели, документы, частые вопросы и отзывы. Списки вроде «Кому подойдёт» заполняются
по одному пункту на строку. Порядок модулей, документов и других элементов меняется перетаскиванием.

При первой установке каталог заполняется данными прежнего сайта (34 программы с обложками,
фото преподавателей и PDF). Повторно это не происходит: правки в админке не перезаписываются.

### Обновление с hse.ru

Каталог два раза в сутки, в 00:00 и 12:00 по Москве, обновляется со страницы
[программ факультета на hse.ru](https://www.hse.ru/edu/dpo/?orgUnit=22753). Запустить вручную —
кнопка «Обновить программы» в списке программ или `docker compose exec app python manage.py sync_catalog`.

- Новые программы на hse.ru добавляются и попадают в направление по названию.
- У остальных обновляются название, формат, даты, цены и описание со страницы программы; если
  какого-то блока на hse.ru нет, прежний текст сохраняется.
- Программы, которые правятся вручную (кнопка «Править вручную» в карточке), не меняются вовсе.
  В списке программ у них нет галочки «Обновляется с hse.ru», по ней же есть фильтр.
- Программы, которых больше нет на hse.ru, скрываются с сайта (не удаляются).
- Тексты программ проходят типограф по брендбуку ВШЭ (`catalog/typography.py`): «ёлочки» и „лапки“,
  длинное тире с неразрывным пробелом, короткое тире в интервалах чисел и времени, неразрывные пробелы
  после коротких слов и у чисел, инициалы через тонкий пробел. Так же обрабатываются начальные данные.
  Поэтому оформление текстов на сайте может отличаться от hse.ru, смысл не меняется.
- Скачиваются недостающие обложки и фото преподавателей, расписания обновляются каждый раз.

Время и история запусков — в админке, раздел «Фоновые задачи»: «Запланированные задачи»,
«Успешные задачи» (там же итог: сколько добавлено, обновлено, скрыто, что не удалось), «Неудачные задачи».

### Главная страница

Карточки направлений, лента ближайших стартов, форматы обучения, «Программы с высоким рейтингом»,
преподаватели и отзывы собираются из каталога при запросе (`GET /api/catalog/landing`): правки в админке
появляются на главной так же, как на страницах программ, с задержкой до 1–2 минут из-за кэша страниц.
В ленту «Программы с высоким рейтингом» попадают только опубликованные программы с заполненным полем
«Высокий рейтинг: место на главной (1–7)», в порядке этого места; свободные места ничем не заполняются,
а если таких программ нет, блок скрыт. У этих программ значок ★★★ с подсказкой «Программа с высоким
рейтингом» — на главной, в каталоге и на странице программы. Преподаватель, у которого в карточке выключено «Показывать
на главной», не попадает в блок «Преподаватели», но остаётся на страницах программ.
Девизы первого экрана — в `frontend/src/data/slogans.json`; после правки списка увеличьте `version`,
чтобы посетители начали новый круг фраз.

### Страница каталога

Каталог — `/catalog` (старые адреса `/Каталог программ.html` и `/catalog.html` перенаправляются,
параметры фильтра сохраняются). Порядок «по каталогу» — как в списке на hse.ru, программы,
добавленные вручную, идут в конце; порядок можно поправить в карточке программы, поле «Порядок в каталоге».
Фильтры, поиск, сортировка и сравнение до трёх программ работают в браузере; ссылки вида
`/catalog?sphere=digital&type=ПК&sort=start&q=право&compare=1,2` открывают каталог с нужным выбором.

### Страницы программ

Адрес страницы — `/programs/<название-латиницей>-<id>.html`, как на прежнем сайте. Если название
программы поменялось, старый адрес постоянно (301) перенаправляет на новый.

Изменения в админке появляются на сайте не позже чем через минуту: страницы собираются из базы
при запросе, nginx держит готовую страницу 60 секунд. Если сервис страниц временно не отвечает,
посетители видят последнюю сохранённую версию.

### Рейтинги, политика, 404, карта сайта

`/ratings` — таблица рейтингов, данные в `frontend/src/data/ratings.json` (строка без места и
ссылки — «Не публиковался»). Своей политики обработки персональных данных у сайта нет: все ссылки
ведут на политику НИУ ВШЭ (`PRIVACY_POLICY_URL` в `frontend/src/lib/brand.ts`), а старые адреса
`/privacy` и `/privacy.html` перенаправляют туда же. Старые адреса `/ratings.html` и `/index.html`
тоже перенаправляются.

`/sitemap.xml` и `/robots.txt` собираются при запросе: адрес сайта берётся из `SITE_URL`, страницы
программ — из каталога (скрытые программы в карту не попадают).

### Баннер статистики и приглашение в канал

Баннер «Согласие на статистику посещений» (кнопки «Разрешить» и «Отказаться») показывается на всех страницах, кроме 404, пока посетитель не ответит;
выбор хранится в браузере. Изменить его можно ссылкой «Статистика посещений» в подвале страницы. На главной после ответа
появляется приглашение в канал Центра в MAX; закрытое приглашение не показывается 30 дней. Адрес и
подпись канала — в `frontend/src/components/landing/ChannelInvite.astro`.

### Ворона и бот поддержки

Ворона в правом нижнем углу (главная, каталог, страницы программ) открывает бота поддержки. Бот
ищет программы и готовые ответы прямо в браузере: текст вопроса на сервер не уходит и нигде не
сохраняется. Список программ для поиска бот берёт из каталога (`GET /api/catalog/bot`), поэтому
правки в админке сразу попадают и в бота. Готовые ответы и честные «на сайте об этом не написано» —
в `frontend/src/data/bot-faq.json`: у ответа есть слова-триггеры, цитата с сайта и ссылка «Подробнее».

### Мини-приложение Telegram

`/tg/` — витрина программ для Telegram: сферы, поиск, карточка программы, заявка. Данные берутся из
каталога при открытии (`GET /api/catalog/tg`). Отправка заявки пока демонстрационная: введённые
данные не покидают телефон, на последнем экране — переход к оплате на hse.ru. Параметр `startapp`
(или `?startapp=` в браузере): `p_<id>` — открыть программу, `c_<метка>` — метка кампании, например
`p_494685723-c_yuriy2`. Чтобы подключить бота, в `@BotFather` в настройках Mini App укажите адрес
`https://<домен>/tg/`.

Пока мини-приложение демонстрационное, на боевом сервере (`SITE_MODE=production`) `/tg/` отвечает 404:
страница загружает скрипт telegram.org и читает имя и фамилию из профиля Telegram, поэтому перед
запуском в рабочем режиме нужна отдельная оценка. На тестовом стенде (`SITE_MODE=test`) страница
работает. После смены `SITE_MODE` в `.env`: `docker compose up -d site`.

## Заявки

Кнопки «Подать заявку» на всех страницах и карточки «Помогите нам стать лучше» открывают одну
форму. Темы: заявка на программу, идея курса, «хочу стать преподавателем», отзыв о работе центра.

Путь заявки: `POST /api/applications` → проверка полей → запись в базу → ответ «принята» → письмо
учебному офису фоновой задачей. Ответ «принята» отдаётся только после записи в базу; недоступная
почта не превращается для посетителя в ошибку. Повтор той же заявки в течение 10 минут не создаёт
дубль. Поле-ловушка отсекает ботов, nginx пропускает не больше 5 отправок в минуту с одного адреса.
IP и браузер посетителя к заявке не прикладываются.

Заявки — в админке, раздел «Заявки»: фильтры по статусу и теме, поиск, смена статуса («Новая»,
«В работе», «Обработана», «Отклонена»), видно, ушло ли письмо и с какой попытки. Кнопка «Проверить почту»
отправляет пробное письмо всем получателям. Каждую ночь в 03:30 удаляются заявки со статусом «Обработана» или
«Отклонена» через `APPLICATION_CLOSED_RETENTION_DAYS` дней после этого итога (по умолчанию 30) и любые заявки
через `APPLICATION_MAX_RETENTION_DAYS` дней после получения (по умолчанию год). Возврат в работу снимает отметку
об итоге.

Кому приходят письма — в админке, «Заявки» → «Получатели писем»: адрес, темы заявок (программы,
идеи курсов, преподаватели, отзывы) и отметка «Получает письма». Получателем может быть только
адрес @hse.ru: в письме все данные заявки. Адрес в другом домене админка не сохранит, а если такой
остался с прежних версий, письма на него не уходят и «Состояние почты» об этом предупреждает.
Пока получателей нет, заявки принимаются и копятся в админке, письма не отправляются.

Если письмо не ушло, сайт повторяет попытку через 5 минут, всего до 3 попыток. После этого письмо
можно отправить вручную: действие «Отправить письмо ещё раз» в списке заявок или кнопка в карточке заявки.

Почтовый сервер — почтовый сервер ВШЭ: сервер, порт, логин и пароль выдаёт ИТ ВШЭ. Он настраивается
в `.env` (без `SMTP_HOST` письма не отправляются):

| Переменная | Назначение |
|---|---|
| `SMTP_HOST`, `SMTP_PORT` | почтовый сервер; 465 — TLS сразу, 587 — STARTTLS |
| `SMTP_USER`, `SMTP_PASS` | учётные данные |
| `APPLICATION_MAIL_FROM` | отправитель (по умолчанию `SMTP_USER`) |
| `SMTP_ALLOW_INSECURE_AUTH` | `1` — разрешить вход без шифрования; только для тестового стенда, в боевом режиме сайт с ней не запустится |

После правки `.env`: `docker compose up -d app worker`.

### Как подключить почту

1. Получите у ИТ ВШЭ параметры почтового сервера ВШЭ: сервер исходящей почты (SMTP), порт, логин
   и пароль ящика, с которого будут уходить письма с заявками.
2. На сервере сайта откройте `.env` в папке установки и заполните `SMTP_HOST`, `SMTP_PORT`,
   `SMTP_USER`, `SMTP_PASS`. `APPLICATION_MAIL_FROM` оставьте пустым — отправителем будет `SMTP_USER`.
3. Перезапустите сайт: `docker compose up -d app worker`.
4. В админке откройте «Заявки»: блок «Состояние почты» над списком показывает сервер, порт,
   шифрование, логин, отправителя и задан ли пароль (сам пароль не показывается).
5. Нажмите «Проверить почту» — пробное письмо уйдёт всем получателям. Результат появится вверху страницы.

В блоке «Состояние почты» также видно, по какой заявке письмо последний раз ушло и последнюю ошибку
отправки. Время в нём — время получения заявки.

## Посещаемость

Сайт сам собирает статистику посещений — без сторонних счётчиков, без IP-адресов и только после
того, как посетитель разрешил статистику в баннере. Браузер отправляет события (`POST /api/collect`): просмотры,
время на странице, прокрутку, переходы, клики по программам и фильтрам каталога, ошибки отправки
заявки. Адрес страницы сохраняется без параметров: из них остаются только `utm_source`, `utm_medium`
и `utm_campaign` (в параметрах ссылок из писем бывают почта и телефон). Лишние параметры отбрасывает
браузер, а сервер проверяет ещё раз. nginx пропускает не больше 600 запросов в минуту с одного адреса.

Сводка — в админке, раздел «Аналитика» → «Посещаемость»: посетители и просмотры, среднее время,
отказы, выводы, популярные страницы и программы, переходы, источники, устройства, активность по
часам, глубина прокрутки, последние сессии; период 7, 30 или 90 дней.

| Переменная | Назначение |
|---|---|
| `ANALYTICS_RETENTION_DAYS` | сколько дней хранить события (по умолчанию 90; старые удаляются каждую ночь в 03:40) |
| `ANALYTICS_MAX_EVENTS` | предел числа событий в базе (по умолчанию 250 000 — примерно прежний лимит 64 МБ); сверх него новые события не записываются |

## Настройки .env

Файл `~/dpo/.env` создаётся при установке и доступен только владельцу. Пример со всеми
переменными — `.env.example`. После правки примените её: `docker compose up -d`.

| Переменная | Назначение |
|---|---|
| `DJANGO_SECRET_KEY` | секретный ключ Django, создаётся при установке |
| `TWO_FACTOR_KEY` | ключ шифрования секретов двухфакторного входа, создаётся при установке (на старых серверах — при обновлении). Без него сайт не запустится; если ключ потерян, двухфакторный вход сбрасывается: `sudo ./scripts/disable-two-factor.sh <логин>` |
| `DJANGO_DEBUG` | `1` только для разработки |
| `DJANGO_ALLOWED_HOSTS` | адреса и домены сайта через запятую |
| `COOKIE_SECURE` | `1` при работе по HTTPS |
| `SITE_MODE` | `production` — боевой сервер (по умолчанию), `test` — тестовый стенд; см. [Боевой и тестовый режим](#боевой-и-тестовый-режим) |
| `SITE_URL` | адрес сайта для канонических ссылок и разметки для поисковиков, например `https://example.com` |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | база MariaDB |
| `DB_ROOT_PASSWORD` | пароль root MariaDB, создаётся при установке |
| `HTTP_PORT`, `HTTPS_PORT` | внешние порты nginx |
| `TLS_DIR` | папка с сертификатом (по умолчанию `/etc/dpo/tls`) |
| `BACKUP_DIR`, `BACKUP_KEEP`, `BACKUP_MAX_AGE_DAYS` | куда, сколько и сколько дней хранить копии (по умолчанию `/var/backups/dpo`, 30 штук, 30 дней) |
| `BACKUP_KEY_DIR` | папка открытого ключа шифрования копий (по умолчанию `/etc/dpo/backup-key`), см. [Шифрование копий](#шифрование-копий) |
| `SMTP_*`, `APPLICATION_MAIL_FROM` | почта, см. [Заявки](#заявки) |
| `APPLICATION_CLOSED_RETENTION_DAYS` | через сколько дней после итога удалять рассмотренную заявку (по умолчанию 30) |
| `APPLICATION_MAX_RETENTION_DAYS` | сколько дней хранить любую заявку (по умолчанию 365; старое имя `APPLICATION_RETENTION_DAYS` тоже работает) |
| `ANALYTICS_RETENTION_DAYS`, `ANALYTICS_MAX_EVENTS` | посещаемость, см. [Посещаемость](#посещаемость) |
| `AXES_LOG_RETENTION_DAYS` | сколько дней хранить журнал входов в админку (по умолчанию 90) |
| `LOG_RETENTION_DAYS` | сколько дней хранить журналы контейнеров сайта (по умолчанию 90) |

> [!CAUTION]
> Не меняйте `DB_NAME`, `DB_USER`, `DB_PASSWORD` и `DB_ROOT_PASSWORD` после установки: база уже
> создана с прежними значениями, и сайт перестанет к ней подключаться.

## Разработка и тесты

Сервер (нужны Python 3.12 и MariaDB):

```bash
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
export DJANGO_SECRET_KEY=dev TWO_FACTOR_KEY=$(openssl rand -base64 32 | tr '+/' '-_') SITE_MODE=test DB_HOST=127.0.0.1 DB_USER=root DB_PASSWORD=<пароль>
.venv/bin/ruff check . && .venv/bin/ruff format --check . && .venv/bin/mypy && .venv/bin/pytest
```

Сайт (нужен Node.js 24):

```bash
cd frontend && npm ci
npm run lint && npm test && npm run build
npm run dev   # http://127.0.0.1:4321, данные берутся из Django :8000 (переменная API_URL)
```

Скрипты: `shellcheck -x -P SCRIPTDIR scripts/*.sh deploy/entrypoint.sh`.

Все проверки повторяются в GitHub Actions (`.github/workflows/ci.yml`) на Ubuntu 24.04:

| Задача | Что проверяет |
|---|---|
| Сервер | ruff, mypy, отсутствие несозданных миграций, файл переводов, pytest |
| Сайт | ESLint, тесты, `astro check` и сборка |
| Скрипты | shellcheck |
| Установка | `install.sh` без параметров на чистой машине, где порты 80 и 443 заняты другим сайтом: выбор портов, администратор, каталог, все страницы, бот, посещаемость, мини-приложение, заявка, перенаправления на HTTPS, скрипты администраторов, резервная копия и восстановление |
